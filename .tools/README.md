# Site checks and builds

Run these commands from the site repository root:

```sh
make -f .zas/Makefile test
make -f .zas/Makefile generate                  # installed Zas
make -f .zas/Makefile publish                   # installs the pinned Zas revision
make -f .zas/Makefile check-vanity
make -f .zas/Makefile check-vanity-live
make -f .zas/Makefile check-microformats
```

`publish` assembles local `.zas/deploy`; the site's Cloudflare Pages Git integration controls actual deployment. The build-only GitHub workflow does not deploy. `vanity-after-deploy.yml` starts on pushes to production `main` (or a manual retry on `main`), then waits up to eight minutes for that exact SHA's completed, successful `Cloudflare Pages` check from the observed Cloudflare app/project, with its deployment-success title and a check suite for the same SHA with `main` or an explicitly null branch. It fails on terminal deployment failures, an unconfirmed result, or timeout; superseded commits are skipped. Only then does it run the shared live checker against `https://dario.cat`, using the deployed commit's baseline. It reads GitHub metadata with `contents: read` and `checks: read`; it never dispatches a deployment. The scheduled/manual monitor remains available independently.

The post-deploy workflow polls the real Cloudflare result because [GitHub restricts `check_run` workflow delivery](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#check_run) for Actions-related suites/SHAs, and this repository currently has no GitHub deployment records to drive `deployment_status`. Cloudflare's exact app/name/project/title filters were verified from its public successful check and suite; provider format changes fail closed. The successful c624d6c production deployment exposed an explicitly null Cloudflare suite branch. The workflow allows that observed case because its own main ref and current-main SHA provide branch identity; a missing field or explicit non-main branch still fails. The corrected gate passed automatically on merged main commit 4f237e9, after the exact Cloudflare Pages deployment succeeded. A live metadata check verifies current public routes, not a cryptographic binding between the custom domain and a particular deployment SHA. An intervening main push is detected before running the checker; later deployment changes remain covered by the recurring monitor. Run the explicit live check after dashboard-only rollbacks or after a deployment that outlasts the polling window.

Both build targets copy working-tree public sources into an isolated tree under `.zas`, omit the seven head-only vanity fragments, and run `zas generate -full -no-plugins`. `publish` installs the immutable Zas revision specified by `ZAS_VERSION` in `.zas/Makefile`; the metadata checker pins the same revision in `.tools/microformats/go.mod`. The current revision also includes the merged safe JSON serialization helpers from Zas PR #115. It supports the site's typed date, summary and canonical helpers, native RSS feeds and rendered Markdown companions through `publish_markdown`. Zas v0.0.7 is the minimum version supporting `-no-plugins`; v0.0.6 lacks that flag. `generate` accepts `ZAS=/absolute/path/to/zas` to test a candidate executable. `publish` installs the pinned revision into `ZAS_BIN_DIR` (default `/tmp/dario-site-zas`). Build failure never falls back to plugin execution.

Cloudflare Pages may check out shallow Git history, which would make source modification dates look like the deployment commit's date. Before installation or assembly, `publish` restores full history with `git fetch --unshallow --no-tags origin` when the repository is shallow, then verifies that the history is complete. The fetch preserves the checked-out commit, including detached Pages checkouts. Builds with full history skip this fetch. A failed fetch or incomplete history stops the build before output can be promoted.

Git selects tracked and nonignored untracked files, including local edits. Hidden account/tool directories, `node_modules`, previous output, and planning/operations documents are excluded. Only `.zas` configuration, `.zas.yml` files, and `.well-known` public paths are allowed hidden inputs. Source symlinks are rejected. Git history remains available through `GIT_DIR`/`GIT_WORK_TREE` against the original repository; it is never copied. Original source mtimes are preserved. A YAML parser rewrites only the staged `zas.deploy` path to keep generation inside the stage; the source configuration is unchanged.

After generation, each raw vanity source is copied byte for byte into its original `name/index.html` path. The checker scans all output HTML, requires the embedded reviewed metadata baseline for all seven routes, and rejects extra routes or `go-source` tags. Its HTML tokenizer accepts existing head fragments and full documents, ignores comments, script strings and escaped examples, and rejects metadata in bodies. Attribute order/case and tuple whitespace do not affect matching; import prefix, VCS and repository identity must remain exact. Duplicate metadata tags fail, including identical tags. Within one tag, the tokenizer retains the first occurrence of each attribute, matching Go discovery. Baseline changes require deliberate review; there is no automatic refresh command.

When native sitemaps are enabled, assembly finalizes `sitemap.xml` after restoring the seven raw vanity pages. It aligns native locations and translation links with each deployed page's canonical URL, preserves native last-modified dates and translation groups, and adds restored vanity entries using source Git dates when available. Complete HTML coverage, local canonical URLs and reciprocal language links are validated before promotion. This site supports one sitemap; sharded output and unfamiliar XML fields fail explicitly, preserving the previous deployment.

With `site.publish_markdown: true`, Zas emits post-template Markdown companions. After assembly, the builder inserts one Markdown alternate link only where the matching deployed `.md` file exists. HTML sources, unpublished pages and the seven raw vanity pages get no invented twins or links. Discovery URLs follow actual filenames, including `index.md`; invalid or duplicate links fail before promotion. The insertion preserves all existing HTML bytes.

The reviewed `.zas/llms.yml` manifest enables agent context assembly. It selects 45 public pages: 22 Catalan, 10 English and 13 Spanish, including all 33 published articles. The root corpus stays Catalan; English and Spanish have separate corpora. Summaries use an H1, a summary blockquote and sections of absolute links to real Markdown companions, with RSS, language cross-links and an Optional link to the matching full file. Full files concatenate the generated companions after template execution, preserving their bytes, with language, source and canonical provenance. Relative links retain each source page's canonical base. No build timestamp is included.

Edit this manifest deliberately when curating new material. A language group has `language`, `title`, `summary`, optional `introduction`, `feed` and ordered `sections`; each section has a `title` and `pages`, whose entries require `source`, `title` and `description`. Sources are repository-relative public Markdown filenames. The compiler checks source eligibility, regular generated Markdown/HTML companions, matching language/canonical metadata and actual RSS artifacts before writing all six context files. Missing or unpublished selections fail the build. Unselected files are never added automatically. CV, private paths, operations documents and drafts stay outside these corpora; the existing public CV JSON is untouched. Project-specific documentation context awaits T24.

Every templated page advertises all three language summaries and its own language's full context. The current-language summary also uses `rel=describedby`, following the current [llms.txt proposal](https://llmstxt.org/); the report's alternate links remain available. Discovery grants exceptions only to the six validated context artifacts and still requires exactly one real page companion where one exists. Missing, duplicate or wrong-language context links fail before promotion. The HTML homepage has no Markdown twin and its context points to About. Raw vanity fragments stay byte-identical. Cloudflare Pages serves the context artifacts as `text/plain; charset=utf-8` with one-hour public caching through `_headers`; individual companions retain `text/markdown`. Request negotiation is handled separately by the generated Pages adapter described below.

With `site.markdown_negotiation: true` and `site.publish_markdown: true`, the guarded build generates `_worker.js` and `_routes.json` inside the final deploy tree. Cloudflare Pages automatically deploys this [advanced-mode Worker](https://developers.cloudflare.com/pages/functions/advanced-mode/) through the existing Git integration and supplies its `ASSETS` binding. Keep the existing production build command and output directory. The separate WebFinger Worker is unchanged. These are server files; no browser JavaScript is added.

The inventory contains only real public HTML pages, their final-byte digests and any validated rendered Markdown companions. It skips raw vanity fragments, CV, private and operational paths before reading content. Pages retains its own pretty-URL redirects; non-index HTML pages also have their actual extensionless aliases. Unknown paths never acquire a guessed Markdown companion. Static subtrees, direct Markdown, feeds, context files, well-known resources and the three existing URL forms of each raw vanity landing page bypass the Worker. Future nested project guides remain eligible. Routing is deterministic and checked against Pages' rule limits.

GET and HEAD requests select Markdown only when its positive effective Accept weight strictly exceeds HTML's. Media ranges, specificity, parameters and explicit exclusions follow [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#section-12.5.1). An absent header or acceptable tie selects HTML. Requests with any `go-get` parameter bypass negotiation. The adapter verifies fetched Markdown against its build digest before serving it; missing twins and Pages' homepage fallback cannot masquerade as Markdown. An unavailable preferred twin falls back to acceptable HTML, otherwise 406. Original asset redirects, errors and unsupported methods remain authoritative. HEAD has the corresponding GET headers and no body.

Negotiated responses merge `Vary: Accept`, carry the robots-aligned Content-Signal and disable browser/shared storage with `private, no-store` and explicit CDN no-store headers. Cloudflare [does not generally use Vary to select CDN variants](https://developers.cloudflare.com/cache/concepts/cache-control/), so shared variant caching is deliberately disabled. HTML and Markdown use separate weak ETags derived from final build bytes. Conditional matching happens after selection; date-only validators are removed so an HTML 304 cannot stand in for Markdown. Page range requests receive the full selected representation; direct assets keep their native validators, caching and range behavior. The adapter also retains the matching Content-Signal on redirects and errors; bypassed static assets use `_headers`.

Node's built-in test runner exercises HTTP selection, failures, validators and bypass behavior without adding packages. Go assembly tests cover inventory integrity, deterministic output, rule limits, reserved collisions and staging failure. Roll back by setting `site.markdown_negotiation: false` and rebuilding: the full staged build removes both generated server files and restores the prior static output. Keep `publish_markdown` enabled to retain direct companions. Do not edit generated files or add root `_worker.js`/`_routes.json` files; reserved collisions fail before promotion.

Both build targets also validate microformats in the completed stage before output is promoted. The hidden `.tools/microformats` module parses HTML with `willnorris.com/go/microformats` and selects the representative identity with its `rhc` helper, rather than relying on item order or accepting an organization card. It pins immutable revision `22f0c2eff25b`; the last tagged release, v1.2.0, does not contain `rhc`. Home and about must identify Dario with the stable homepage URL/UID, a local avatar, the public email and all seven verification profiles. Every public post must retain its source name, content, author, canonical URL, summary, tags, language and available publication/update instants. The checker reuses metadata helpers from the same pinned Zas revision as production. Only tracked source history supplies a missing update date; publication dates are never inferred from Git.

The three archives must contain exactly their source-derived article sets, with no duplicate URLs, visible language labels and the known publication precision. Currently there are 33 public local posts, 30 explicit publication instants and three sourced partial dates; the combined archive also retains two separately marked external citations. The live draft URL remains generated but cannot become an entry or appear in an archive. The checker also validates the six dated slash entries, project items, slash-index updates and the dated talks against their existing public sources. It preserves day precision on events and does not invent timestamps for undated talks.

The same checker validates one JSON-LD object in each rendered page's head, with a shared `Person` and a `BlogPosting` only for eligible public articles. Identity, local avatar, job and the seven verified profiles must agree; article title, canonical URL, description, tags, language and known dates must match public sources and the existing microformats checks. Unknown dates are omitted, including the three partial publication dates. Date offsets and fractional seconds are preserved. Only the seven reviewed raw vanity fragments bypass the layout; they must remain free of JSON-LD. Duplicate JSON keys, malformed or quoted documents, duplicated/misplaced scripts, missing Sifa or Speaker Deck links and invented article nodes fail validation. Escaped quotes, ampersands, Unicode and script-like text round-trip as data in local fixtures. An unrelated Cloudflare beacon does not alter the metadata checks. Project source-code schemas remain deferred until the docs pipeline establishes their repository and licence facts.

Checks perform no HTTP requests, process no CV data and exclude hidden tooling and private planning artifacts from output. Unit tests use local HTML fixtures and deliberate semantic failures, including organization identity, wrong timezone or author, empty content, missing/duplicate entries, draft exposure, hidden language labels and invented event times. The article content adapter supports the current literal sources; a future article containing a Go template action or embed fails explicitly until its rendered-source adapter is added. The contact page's existing public HTML fragment is the only embedded source supported for slash-page checks.

Run the checker separately against any completed deployment with explicit source and output roots:

```sh
go -C .tools/microformats run -mod=readonly ./cmd/microformats -root ../.. -dir ../../.zas/deploy
go -C .tools/microformats test -mod=readonly ./...
```

`make test` runs both isolated tooling modules and the dependency-free HTTP adapter tests with Node.js 24 or later. The production build remains Go-only. The Site checks workflow caches both pinned dependency sets and uses the same protected `publish` command configured in Cloudflare Pages. A failed or unavailable microformats checker stops staged assembly before the previous deployment is replaced.

The live CLI is independent of its working directory:

```sh
go -C .tools/vanity run ./cmd/vanity -live -base-url https://dario.cat -timeout 10s
go -C .tools/vanity run ./cmd/vanity -dir ../../.zas/deploy
```

It checks both bare and trailing-slash paths with `?go-get=1`, final HTTP 200 and `text/html`, and the same exact metadata. HTTPS redirects must stay on the same host/port and preserve the query; at most five redirects and 1 MiB per response are allowed. The timeout includes redirects for each of fourteen requests. No module checkout or Git host availability is required. These checks verify import discovery metadata, not repository contents or every package subpath.

Only checked output is promoted using same-filesystem directory renames. Normal promotion failure restores the old deployment. This is not a filesystem transaction: a process/host crash between renames can leave the old tree under `.zas/.site-build-*/previous-deploy`. Recover that tree before deleting the stage. A stale `.zas/.site-build-lock` may be removed after confirming no build is running. A failed generation or validation leaves the previous deploy untouched. Build tests exercise that behavior, secret exclusions, Git history access, raw byte preservation and promotion rollback; live tests use local TLS HTTP servers.
